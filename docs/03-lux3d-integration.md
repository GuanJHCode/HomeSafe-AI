# Lux3D 资产、生成任务与预算

本文整理[交接摘要](../materials/source/handoff-summary-20261103.txt)中的方案。官方接口、计费、授权和赛事规定尚未在本次独立核验。

## 主路径：手动生成与导入

先用占位模型开发核心流程，同时尽早在 Lux3D 生成椅子与柜子各一个小样，下载 GLB 并保存来源和生成过程。通过 `AssetService` 导入、验证、校准与批准后替换视觉模型，再补齐其余核心家具。

建议的每项资产记录包括：本地资产标识、生成平台与任务线索、生成/下载日期、输入素材及其授权、原文件、校准记录、审核状态、使用场景与衍生文件关系。此清单是本次补充的记录建议，尚非已存在的 Schema。

校准需核对方向、比例、单位、原点和加载复杂度。模型外观替换不应改变场景对象编号、已确认尺寸、规则关联或历史记录。

## 可选路径：应用内生成

核心闭环稳定后，再实现：

```text
管理员上传素材并确认预算
→ GenerationService 创建本地任务
→ CreditBudgetService 预留内部预算
→ GenerationWorker 经 AholoSdkGateway 提交
→ 关联并轮询同一个官方任务
→ 下载、验证并持久化模型
→ 人工校准与批准
→ 加入场景
```

具体调用顺序、持久化事务和失败补偿需在工程阶段明确；图中为职责流程，当前没有运行中的服务。

## 防止重复收费的约束

- 收费调用默认关闭；开启前确认真实权限、可用预算与实际价格。
- 本地请求需要幂等控制；重启后恢复已有任务关联。
- 创建请求超时不代表供应商未受理，不能自动重复创建。
- 无法确定是否受理的任务必须先核查与对账，再决定下一步；不要把未知状态视为可安全重试。
- 轮询应查询同一个任务；查询重试不能隐式转成再次创建。
- 失败不应破坏已导入的可用样例。

摘要称生成结果链接约两小时有效，应及时持久化。该时效未在本次核实，实施时以当前官方契约为准，并验证过期、下载中断和恢复行为。

## 3300 积分的使用边界

“3300 积分”是来源摘要中的预算背景，不是本次已核验的账号余额。内部预留与实际消费必须分账；不能按每次固定 1 积分估算，也不能宣称自动同步官方余额。

建议先给小样、核心资产、可选增强分配预算，逐次记录实际扣分。创建结果不明时保留待核对记录，确认后再核销或释放预留。
